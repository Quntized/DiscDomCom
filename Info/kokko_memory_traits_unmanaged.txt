Output Explanation

When you execute:
C++

std::cout << "Original Layout: "
          << layout_info.dimension[0] << "x" << layout_info.dimension[1] 
          << "another info , if exist: " << layout_info.dimension[2] 
          << "another info , if exist: " << layout_info.dimension[3] << "\n";

It will likely output: Original Layout: 10x10another info , if exist: 1another info , if exist: 1

Why the "1"s?

    layout_info is an object of type Kokkos::LayoutRight.

    This struct typically holds an array of dimensions (often size 8).

    Your view is Rank 2 (2D). So dimension[0] and dimension[1] are set to 10.

    For dimensions that are not used (Rank > 2), Kokkos often defaults them to 1 (or sometimes 0, depending on the version) so that stride multiplication logic (N×1=N) remains safe.

2. Code Explanation: The "Unmanaged View"

This block of code creates a Ghost View (Shadow View) that looks and acts like a normal array but does not own the memory it uses.
C++

using UnmanagedViewType = Kokkos::View<double**, Kokkos::LayoutRight, 
                                       Kokkos::HostSpace, 
                                       Kokkos::MemoryTraits<Kokkos::Unmanaged>>;

The Template Parameters:

    double**: It is a 2D array of doubles.

    Kokkos::LayoutRight: It uses Row-Major layout (standard C++).

    Kokkos::HostSpace: The data lives in CPU RAM.

    Kokkos::MemoryTraits<Kokkos::Unmanaged> (THE KEY PART):

        This flag tells Kokkos: "Do NOT allocate memory. Do NOT free memory."

        This View is just a "window" or a "lens." It assumes someone else (the parent view) is responsible for the memory's lifetime.

The Constructor:
C++

UnmanagedViewType shadow_view(raw_ptr, layout_info);

    raw_ptr: You pass the raw memory address (double*) that you extracted from the parent view earlier.

        Analogy: You are giving the keys to an existing house.

    layout_info: You pass the dimensions/strides object you extracted from parent.

        Analogy: You are giving the blueprint of the house so the new View knows how big the rooms are.

The Result:

shadow_view is now a fully functional Kokkos::View. You can access shadow_view(5,5), iterate over it, or pass it to kernels.

    Safety: If shadow_view goes out of scope, nothing happens (memory stays).

    Danger: If parent dies first, shadow_view becomes a Dangling Pointer. Accessing it will crash the program.

Summary

This technique is used when you need to wrap External Data (like a raw pointer from C, Fortran, or another library like DDC) inside a Kokkos::View so you can use Kokkos algorithms on it without copying the data.
